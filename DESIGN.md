# Payment Collection Agent — Design

## 1. Architecture overview

The deterministic state machine, validators, side-effects, and message templates own everything in this agent. The LLM is consulted exactly once per turn for slot extraction and 3-way intent classification (AFFIRM / NEGATE / AMBIGUOUS) — it never drives state transitions, never sees account data, never composes spec-required user-facing prose, and never sees the assembled conversation history on subsequent turns.

| Module | Responsibility | Imports `anthropic`? |
|---|---|---|
| `agent.py` | Per-turn orchestration: extract → cancel guard → merge → transition → drive loop → render | no |
| `state.py` | 16-stage enum, slot store, transition functions (pure of `(state, slots, counters, extraction)`) | no |
| `extract.py` | The single LLM call per turn. Tool-use schema for slots + intent. | no (consumes `llm.py`) |
| `llm.py` | Thin Anthropic SDK wrapper. Determinism contract enforced here. | **yes (only module)** |
| `api.py` | HTTP client. Asymmetric retry per DECISIONS #13. Redacted logging. | no |
| `validate.py` | Pure validators: Luhn, expiry, DOB strict-parse, amount, account-id format | no |
| `verify.py` | Strict-equality identity comparators (canonicalized name + secondary factor) | no |
| `templates.py` | `render(slots, message_key) → str`. All user-facing prose. | no |
| `redact.py` | CVV/PAN/PII scrubbing helpers + canonical placeholder | no |
| `errors.py` | Typed exception hierarchy (`PaymentAgentError`, `AgentInternalError`, …) | no |
| `config.py` | Pinned constants. Single source of determinism contract + retry caps + timeouts. | no |
| `cli.py` | Thin REPL wrapper | no |

The shape was chosen over a fully LLM-driven agent because the rubric weights reliability and failure handling, and reliability is only credibly demonstrable when the assertions are deterministic. State transitions are pure functions of `(state, slots, counters, extraction)`, so every retry edge, every cap, every cancellation point gets a unit test that fails on a real defect rather than a model regression. API payloads are pure functions of `(state, slots)`, so request shape and error mapping are mockable end-to-end. The only non-deterministic surface is the per-turn extraction call, which is bounded by an eval corpus + scorer (`eval/extractor_eval.py`) rather than a unit test — the right tool for behavior under messy input. A fully LLM-driven agent would have made every assertion in the eval probabilistic, undermined the determinism story, and forced the design doc to argue from anecdotes rather than tests. The single-call-per-turn ceiling also bounds cost and rate-limit exposure by construction.

## 2. Key decisions

Curated from the 28 in `DECISIONS.md` — the ones most likely to surprise a reviewer who hasn't seen the brainstorm.

**Verification interaction — field-level transparent failure (DECISIONS #2).** When a verification field fails strict match, the agent names the failed field and offers the remaining secondary factors ("That DOB doesn't match — try again, or share Aadhaar last-4 / pincode"). The pattern is friendlier for legitimate fat-finger users and doesn't reveal what the actual value on file is, since the user's submitted value is what's named. Considered and declined: opaque "verification failed, please try again" — paranoid-safe but UX-hostile, and the residual attack surface (secondary-factor enumeration) is the same in either pattern. The enumeration risk is acknowledged as a documented residual risk; production fix is rate-limiting per account.

**Slot mutability — lock once filled, four orchestrator-controlled carve-outs (DECISIONS #21).** A slot, once filled, cannot be overwritten by user-stated mid-flow correction; "wait, my DOB is actually X" is rejected with a cancel-and-restart prompt. Four carve-outs are orchestrator-controlled, never user-controlled: typo-class payment failure clears the named card field, DOB disambiguation resolution writes the slot, lookup `account_not_found` clears `account_id`, verification failure clears the failed name and/or factor slot. Considered and declined: free-form user-controlled correction at any stage — would make the 3-way intent classifier responsible for distinguishing "fills new slot" from "corrects existing slot," and would let an attacker pivot mid-verification to a different (name, factor) tuple than the one that started the cycle.

**Asymmetric API retry — the idempotency argument (DECISIONS #13).** `lookup_account` retries silently once at 500ms backoff (per-attempt 4s, total budget 10s); `process_payment` is **never** retried on transient failure (per-call 30s) and routes to `terminal_payment_unknown` with conservative copy. The asymmetry tracks idempotency: lookup is safe to retry, payment isn't, and the spec API doesn't accept an idempotency key — so a transient retry on payment risks double-charging the user. The asymmetry between "double-charge" (user money) and "ghost charge" (user inconvenience plus a support call) makes over-conservatism the rubric-safe default. Considered and declined: symmetric retry policy — production-correct only with idempotency keys, which the spec API doesn't support.

**Hybrid templating — three determinism bars (DECISIONS #8).** State transitions are bit-exact deterministic, pure functions of `(state, parsed_input)`. API payloads are bit-exact deterministic, pure functions of `(state, slots)`. Message text uses templates for spec-required content (verification verdict, balance display, transaction ID, recap) and is asserted as exact strings; free-form connective prose is asserted on properties (contains last-4, contains "verified," excludes DOB) instead of equality. Anthropic doesn't guarantee bit-exact determinism even at `temperature=0`, so message text isn't asserted as a single bar across the board — but the three layers each get the bar that's actually defendable, which lets eval personas assert on `final_stage`, counters, and `transaction_id` rather than on `response["message"]`. Considered and declined: full template-based prose with no LLM in the message path — possible, but the conversational quality cost is real and the determinism bar isn't even buying anything (the message isn't an assertion target).

**Terminal-state lifetime — one tick, then auto-route to `closed` (DECISIONS #11 + #23).** Six terminal states (`terminal_completed`, `terminal_verification_exhausted`, `terminal_payment_exhausted`, `terminal_cancelled`, `terminal_account_not_found`, `terminal_payment_unknown`) each emit cause-specific copy on the turn that produces them, then on the next `next()` call the orchestrator routes to a shared `closed` state before consulting the extractor. Eval can read `state == terminal_X` end-of-turn, the user gets the right cause-specific message once, and subsequent calls return the generic "this session has ended" copy without burning an LLM call. Considered and declined: keep terminal stages as the resting state forever — would conflate "first time in terminal" with "subsequent call" at the assertion layer, and would re-spend an LLM call on every closed-session call.

**DOB disambiguation — two-option choice with year-carrying resolution.** The default DOB reading is DD-MM-YYYY (Indian context); when both readings produce plausible dates within ~1925–today, the agent stores both readings in disambiguation slots (without pre-committing either to the verified DOB slot) and prompts the user to choose: "That date is ambiguous — could it be April 5, 1990 or May 4, 1990? Please reply with the correct date." The user can reply with the date in any form — "May 4", "the second one paraphrased back as a date", or a different date entirely. Resolution does a `(month, day)` match against the stored options, so "May 4" without a year resolves to 1990-05-04 (the stored year carries through, the user doesn't have to retype it). A response that matches neither stored option falls into a carve-out path: the user is providing a different date entirely, so it's written through. Strict parsing via `datetime.date(y, m, d)` catches the leap-year canary (1988-02-29 valid; 1989-02-29 raises) — verified end-to-end by the `leap_year_acc1004` persona. Considered and declined: the simpler "render the primary, ask for a yes/no" pattern — pre-commits to a parse, and the binary affirm doesn't degrade gracefully when the user's "yes" turns out to be wrong (silently consumes a verify retry).

**Architecture commit — `llm.py` is the only module that imports `anthropic`.** Centralizes the determinism contract (`temperature=0`, `thinking={"type":"disabled"}`, pinned model `claude-sonnet-4-6`) at one site. `tests/test_llm_kwargs.py` asserts a closed whitelist of kwargs on every call: `{model, temperature, thinking, max_tokens, system, messages, tools, tool_choice}` — adding a new kwarg silently breaks the test, defending the contract at the type level. Considered and declined: per-call SDK access from `extract.py` and `agent.py` — convenient short-term, but every new caller would have to remember to pass the determinism kwargs, and the contract becomes a code-review obligation instead of a test invariant.

## 3. Tradeoffs accepted

Considered and declined for this submission. Each entry: what it is, why we declined, what production would change.

**LLM-as-judge eval (DECISIONS #9).** A second LLM pass evaluating persona transcripts for natural-feel and spec-adherence was considered and declined — the deterministic kernel makes most assertions programmatic by design, and a second LLM pass would exceed the assignment's scope without adding rubric value beyond what the corpus + scorer already measures. At production scale this becomes valuable for daily-slice drift detection over real transcripts.

**Multi-payment per session (DECISIONS #6).** One payment per `Agent` instance was the chosen scope; allowing a second payment requires a fresh `Agent()`. The API doesn't persist balance updates, so a second payment runs against the original balance and the divergence between session-tracked remaining-balance and server-truth deepens with each transaction. Production fix is either an idempotency key + per-payment session reset, or server-side balance-of-record updates — both out of scope for the take-home.

**Prompt-injection defense (DECISIONS #16).** No defensive coding for jailbreak-style inputs because the LLM's blast radius is bounded by the architecture: it sees only extraction prompts (never account data, never conversation history past the current turn), can't bypass the state machine, and can't trigger payment. Production agents that move toward conversational free-form responses or LLM-driven flow would need input policy filters and extracted-output schema validation; this agent already does the latter at `_parse_tool_input`.

**CVV-specific cap of 3 (DECISIONS #4).** A single typo-class cap of 5 was chosen instead of the bank-standard CVV-specific cap of 3 — simpler to explain in the design doc, and the take-home UX cost is negligible. Production gets a CVV-specific counter and one extra branch in `_handle_payment_result`.

**Per-field retry counters (DECISIONS #3).** Per-cycle counters were chosen over per-field counters because a per-field budget invites the "bash the same wrong DOB three times then switch to Aadhaar" attack, while per-cycle closes it cleanly at the cost of a slightly less expressive failure message. Production wants per-field counters plus a global session cap with rate-limit-style escalation.

## 4. Where the agent struggles

Honest list. The brief explicitly asks for this.

**Long-tail extractor miss: `aadhaar_explicit_factor`.** Input "last 4 digits of my Aadhaar are 1234" extracts `aadhaar_last4="1234"` correctly but leaves `selected_secondary_factor=None`. The polite-refusal prompt fix in Step 8 made the model conservative on `selected_secondary_factor` to avoid setting it on NEGATE inputs ("I don't want to give my DOB"), and the conservatism overshot this case. Functional impact is zero — `state._selected_or_inferred_factor` infers the factor from value presence — but the corpus assertion fails and is documented in the case's `notes` field. The fix path (refine the prompt to distinguish "user names a factor positively" from "user refuses a factor") risks regressing the polite-refusal critical-subset case; that tradeoff is the kind of thing eval iteration is designed to surface.

**Long-tail extractor miss: `name_with_extra_whitespace`.** Input "I am Nithin   Jain" (triple internal space) is normalized by the model to "Nithin Jain" despite the tool-schema description saying "capture exactly as stated." Functional impact is again zero — `verify._canonicalize_name` collapses internal whitespace before strict comparison anyway — but the case surfaces a real-world pattern worth naming: prompt instructions are statistical, not contractual. The LLM's training prior on whitespace normalization in named-entity extraction is strong enough to override an explicit instruction in some inputs. Architecture should not depend on prompt instructions where a deterministic post-process exists, which is why verification's strict-equality compare runs through `_canonicalize_name` rather than trusting the extractor's output verbatim.

**Stub CVV behavior — typo-recovery persona scope-shifted.** The prodigaltech.com stub appears to accept any well-formed CVV (3–4 digits), so a persona that submits CVV `999` with a Luhn-valid PAN gets `payment_success` instead of `INVALID_CVV`. The original `payment_typo_recovery` persona was renamed `insufficient_balance_recovery` and re-targeted to the broader "payment failure → user corrects → success" loop using ACC1001 + amount > balance. The API-driven typo-class recovery path (carve-out #1 clears the named field, payment_retries increments) is exercised in `tests/test_agent.py::test_payment_typo_recovery_clears_failed_field_and_succeeds` via mocked api responses; the live persona just can't reproduce it against the real stub.

**First-turn greeting-prefix UX tradeoff.** When the user types something on the very first turn instead of the empty bootstrap (e.g. "hi" instead of letting the CLI auto-greet), the agent skips the "Hello! I'm here to help you make a payment" prefix and goes straight to "Could you share your account ID?" The drive loop emits the LAST message_key in the chain, and the GREETING → COLLECTING_ACCOUNT_ID transition advances past `greet_advance` to `prompt_account_id`. Chaining message_keys (e.g. join with "\n\n") would fix the UX, but at the cost of more orchestrator complexity and harder test assertions. The CLI works around it by calling `agent.next("")` once before the input loop, which fires the GREETING-bootstrap branch and emits the greet template without transitioning. The polite-prefix cost on direct-`Agent.next` callers is small enough to accept.

**Disambiguation success path is deterministic in code but constrained in live testing.** The four real test accounts in the spec stub have these DOBs: ACC1001 1990-05-14, ACC1002 1985-11-23, ACC1003 1992-08-10, ACC1004 1988-02-29. Of these, only ACC1003's DOB produces parser-ambiguity (input "10-08-1992" parses as both Aug 10 DD-MM and Oct 8 MM-DD with both dates plausible) AND has the primary reading match the on-file value. Even so, live testing reveals the LLM extractor doesn't reliably flag "10-08-1992" as ambiguous — the model's training prior on Indian DD-MM-YYYY is strong enough to skip the alternate flag — so the success path through dob_disambiguation rarely fires against the real spec accounts. The success path code is correct (verified by `test_dob_disambiguation_resolved_advances_to_collecting_amount_when_verify_passes` covering the AFFIRM branch and `test_dob_disambiguation_resolved_via_carve_out_advances_when_verify_passes` covering the explicit-alternate branch), but reproducing it manually requires either a synthetic test account or an input format the LLM more reliably flags ("05-04-1990" triggers ambiguity flagging consistently in our runs, but for the spec accounts that input never matches an on-file value). This is a real-world testability gap, not a code defect — documented here rather than worked around because the design doc is the right place to surface "what we couldn't reproduce against the spec stub" rather than ship synthetic accounts that obscure the asymmetry between deterministic code coverage and live-stub coverage.

**Drive-loop bugs caught only by integration and manual testing.** Three real defects in `agent._drive` were surfaced by methods other than unit tests. (1) After a verify failure, the redundant `step_on_entry` call re-evaluated the now-cleared dob slot and overwrote `verify_fail_dob` with the generic `prompt_identity` — users saw "I've found your account" repeated instead of "That date of birth doesn't match." Caught by reading captured persona transcripts. (2) After verify success, `step_on_entry(COLLECTING_AMOUNT)` returned `prompt_amount` (no balance) and overwrote `entry_collect_amount` (which carries the DECISIONS #28 balance share) — users saw "How much would you like to pay?" instead of the verified+balance copy. Caught by reading captured persona transcripts. (3) After dob_disambiguation resolved, the message-key preservation logic added to fix (2) was too coarse — when entry's verify run failed, the routing's "Got it." overwrote `verify_fail_dob` and silently consumed a retry. Caught by manual testing (a single ACC1001 → ambiguous-DOB → resolve session in the CLI). Fix narrowed the preservation rule: only preserve when entry was a true no-op (no slot mutation, no counter increment). All three are fixed; all three have regression tests. The takeaway is concrete: the persona suite, manual smoke testing, and the unit suite catch different defect classes. Semantic message-key drift across a real conversation isn't visible from any single test layer. Eval and manual testing are not optional, even on a heavily-unit-tested deterministic kernel.

## 5. What I'd improve with more time

Prioritized engineering decisions, not a wishlist.

**Typed `AgentInternalError` at the harness level — because "any exception is a persona failure" conflates three different things.** `AgentInternalError` is defined and caught at `Agent.next`'s boundary today (converts to a closed-session message). The eval harness's per-case `except Exception` then surfaces every exception as a persona failure, which conflates user-meaningful agent errors, harness/infra errors (network, JSON parse), and corpus-author errors (typo in slot field name). Each deserves a different exit code and reporting path — corpus-author errors should fail loudly up front before any persona runs.

**Idempotency keys on `process_payment` — because the asymmetric retry is a workaround, not a fix.** The `terminal_payment_unknown` outcome exists because we can't safely retry payment without an idempotency key, which the spec API doesn't accept. Client-generated UUID per attempt + server-side dedup unlocks safe retry on transient failures, which converts `terminal_payment_unknown` from a terminal state to a recoverable one. The architecture is ready for it (api.py is already the single retry-policy site); the API would need a `payment_id` request field.

**Per-error-class LLM failure handling — because flattening SDK errors makes auth bugs look like rate limits.** `agent.py` catches `LlmCallFailed` and degrades to AMBIGUOUS-then-re-prompt; `llm.py` flattens `AuthenticationError`, `RateLimitError`, `APIConnectionError`, etc. into a single exception class. Auth failures (401) are unrecoverable and should terminate the session with a "service unavailable" message; rate limits (429) should retry with backoff; transient network errors should retry once. The `LlmCallFailed` class needs to either carry an error-class enum or split into typed subclasses.

**Structured logging with a redaction filter — because `print` to stderr is the wrong observability primitive past prototype.** `api.py` writes the redacted 5-field payment-attempt record (`account_id, amount, attempted_at, error_class, last4`) via `print`, and `agent.py` writes invariant-violation warnings to stderr. Stdlib `logging` with a JSON formatter, a `redact.py`-driven filter, and per-module log levels gets us grep-able fields (account_id, persona_id, request_id) for production dashboards. The redaction primitives are already centralized in `redact.py`; only the formatter and filter need writing.

**Tokenized card references — because handling raw PAN and CVV in conversation is a PCI scope nightmare.** The current architecture takes raw card details from the user and puts them in the LLM extraction prompt and the API request body. A production deployment should accept a tokenized card reference from a PCI-compliant front-end (Stripe Elements, Adyen Drop-in style) and never see PAN/CVV in conversation at all. This is the architecturally correct move; the take-home submission keeps raw card handling because the spec API expects PAN/CVV in the request body.
